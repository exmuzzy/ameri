# Промпт для агента: план создания Telegram-бота для управления работой менеджеров

> Скопируйте всё, что ниже линии, и передайте агенту (Claude Code или другому агенту-планировщику).
> Агент должен **только спланировать** работу, код он пока не пишет.

---

## Роль

Ты — архитектор программного обеспечения и технический лид. Твоя задача — **исследовать индустрию, составить опросник для заказчика и подготовить подробный план реализации** Telegram-бота. Код на этом этапе не пишешь. Результат сохраняешь в текущий репозиторий.

## Контекст

- Название бота будет определено позже. Везде используй плейсхолдер `<BOT_NAME>` и вынеси имя в конфиг.
- Текущий репозиторий — это **единый источник правды**: в нём живут код бота, конфигурация групп и тем, роли и права пользователей, типовые действия (меню), правила харнеса для LLM и история его изменений.
- Под «Z-кодом» в требованиях заказчика, скорее всего, имеется в виду **Claude Code**, работающий с моделью **DeepSeek** через её Anthropic-совместимый API. Прими это как рабочую гипотезу, но **обязательно вынеси в опросник** вопрос подтверждения и перечисли альтернативы (OpenCode, Aider, собственный агентный цикл поверх DeepSeek API и т. п.) с плюсами и минусами.

## Что должна делать система (требования заказчика)

### 1. Размещение
- Бот работает на сервере в интернете (VPS или облако), доступен 24/7.
- На этом же сервере установлен Claude Code (или альтернатива), настроенный на модель DeepSeek. Бот вызывает его для обработки части запросов менеджеров.

### 2. Роли и права
- **Менеджеры** (двое и больше). Их имена и Telegram ID известны системе. У каждого есть набор прав (грантов): что ему разрешено делать с ботом.
- **Руководители** (один или несколько) и **администратор**. Они видят всё, что делают менеджеры, настраивают права, меню и харнес.
- Права хранятся в репозитории (декларативно, например в YAML) и/или в БД. Изменения прав должны оставлять след (кто, когда, что изменил).

### 3. Группы и темы
- Бот может работать в **нескольких Telegram-группах**. Каждая группа закреплена за своей темой (или используются Topics внутри супергруппы — это нужно сравнить).
- В каждой группе: бот с правами администратора, один или несколько менеджеров, один или несколько руководителей.
- Конфигурация «группа → тема → участники → доступные действия → правила харнеса» описывается в репозитории.
- Предусмотреть возможность **нескольких ботов** (разные токены, разные наборы групп) в одной кодовой базе.

### 4. Работа менеджеров
- Менеджеры пишут в группу, загружают файлы, задают вопросы, переписываются между собой.
- К боту они обращаются в основном через **команды и типовое меню** (`/start`, `/help`, `/menu` и действия, определённые руководителем), а не свободным диалогом с моделью.
- Прямой доступ к модели DeepSeek у менеджеров ограничен или отсутствует — только то, что разрешил руководитель.
- Все сообщения, вопросы, файлы, ответы бота сохраняются: **история работы** каждого менеджера по каждой группе. Нужно продумать, что хранится в git-репозитории (конфиги, правила, выгрузки/отчёты), а что — в БД и объектном хранилище (сырые сообщения, файлы), и почему.

### 5. Типовые действия (меню)
- Руководитель определяет набор типовых действий (например: «сделать сводку обсуждения», «проанализировать загруженный файл», «подготовить ответ клиенту», «составить отчёт за день») и хранит их в репозитории как шаблоны: название, описание, кто может вызывать, в каких группах, какой промпт/скилл, какие входные данные нужны.
- Добавление нового действия не должно требовать правки кода — только конфиг/шаблон.

### 6. Пульт руководителя
- Руководитель может:
  - смотреть, что происходит в любой группе (лента активности, файлы, вопросы, ответы бота, статистика по менеджерам);
  - спросить у бота прямо в Telegram (в личке) «что происходит в группе X», «что сделал менеджер Y сегодня»;
  - работать из Claude Code на сервере или локально с тем же репозиторием;
  - поручить боту написать конкретному менеджеру конкретный ответ;
  - указать на плохой ответ: «ты ответил так-то, а надо было так-то, исправь ответ и запомни это».
- Сравни варианты пульта: команды в Telegram-личке, Telegram Mini App, веб-админка, только Claude Code + репозиторий. Предложи рекомендацию для MVP и для следующих этапов.

### 7. Самообучающийся харнес
- Харнес — это системные промпты, правила, few-shot примеры, скиллы, инструменты и ограничения, с которыми бот вызывает модель. Он хранится **в этом репозитории** и постоянно пополняется.
- Когда руководитель исправляет ответ, система:
  1. отправляет исправленный ответ менеджеру;
  2. предлагает (или создаёт) новое правило/пример в харнесе;
  3. сохраняет изменение как коммит или pull request с понятным описанием, чтобы руководитель мог отсмотреть и откатить.
- Руководитель должен видеть все действующие правила: глобальные, по теме/группе, по типовому действию.
- Нужны защиты: правило не применяется без подтверждения руководителя (или применяется в режиме «черновик»), есть версионирование, откат, проверка на противоречия между правилами, регрессионные проверки (eval) на наборе эталонных вопросов.

## Задание

### Шаг 1. Исследование индустрии
Изучи, как такие задачи решаются сейчас, и кратко опиши найденное со ссылками. Минимум:
- фреймворки Telegram-ботов (aiogram, python-telegram-bot, grammY, Telegraf) — работа с группами, топиками, файлами, правами администратора, webhook vs long polling;
- запуск Claude Code в headless/SDK-режиме (`claude -p`, Claude Agent SDK), подключение к DeepSeek через Anthropic-совместимый endpoint, CLAUDE.md, skills, hooks, subagents, ограничение инструментов и прав;
- альтернативные агентные рантаймы (OpenCode, Aider, LangGraph, собственный цикл tool-calling поверх DeepSeek API);
- подходы к «памяти» и самообучению агентов: память в файлах/репозитории, rule files (CLAUDE.md, `.cursor/rules`), RLHF-подобная обратная связь от человека, prompt versioning, eval-наборы (promptfoo, DeepEval и т. п.), human-in-the-loop;
- RBAC/ABAC для ботов, аудит-лог, хранение персональных данных (в т. ч. 152-ФЗ, если данные граждан РФ), шифрование, бэкапы;
- существующие продукты похожего класса (корпоративные AI-ассистенты в мессенджерах, CRM-боты) — что у них можно взять.

### Шаг 2. Опросник для заказчика
Составь опросник, который поможет выбрать, что из найденного нужно. Формат: вопрос → варианты ответа → твоя рекомендация по умолчанию → на что влияет ответ. Обязательно охвати:
- подтверждение, что «Z-код» — это Claude Code, и готовность к альтернативам;
- число менеджеров, руководителей, групп и ботов сейчас и через год;
- отдельные группы по темам или одна супергруппа с Topics;
- какие типовые действия нужны в первой версии (дай список из 10–15 кандидатов на выбор);
- разрешён ли менеджерам свободный вопрос к модели и с какими лимитами;
- типы и размеры файлов, нужно ли распознавание (PDF, DOCX, XLSX, изображения, голосовые сообщения);
- где хранить историю и файлы, срок хранения, требования к ПДн и локализации данных;
- выбор хостинга (страна, провайдер, бюджет), нужен ли домен и HTTPS;
- вид пульта руководителя для MVP;
- как утверждаются новые правила харнеса: автоматически, после подтверждения, через pull request;
- бюджет на токены DeepSeek, лимиты на пользователя и группу;
- язык интерфейса, часовой пояс, рабочие часы;
- интеграции (CRM, Google Drive, почта, 1С и т. п.) — сейчас или позже;
- требования к мониторингу, уведомлениям и бэкапам.

### Шаг 3. План реализации
На основе исследования и **рекомендаций по умолчанию** (ответы заказчика придут позже) подготовь план:
1. **Архитектура** — схема компонентов (Mermaid): Telegram → бот → очередь задач → воркер с Claude Code/DeepSeek → БД / файловое хранилище / git-репозиторий харнеса → пульт руководителя. Обоснуй выбор стека.
2. **Структура репозитория** — дерево каталогов с назначением каждого, например:
   - `bots/` — конфиги ботов;
   - `groups/` — группы и темы;
   - `users/` и `roles/` — пользователи, роли, гранты;
   - `actions/` — типовые действия (шаблоны меню);
   - `harness/` — системные промпты, правила (глобальные / по теме / по действию), примеры, скиллы, `CLAUDE.md`;
   - `evals/` — эталонные вопросы и ожидаемые ответы;
   - `src/`, `deploy/`, `docs/`.
3. **Модель данных** — сущности и связи: Bot, Group, Topic, User, Role, Grant, Action, Message, File, BotResponse, Correction, HarnessRule, AuditEvent.
4. **Модель прав** — матрица «роль × действие», как проверяются гранты, как руководитель их меняет.
5. **Сценарии** (пошагово, с примерами сообщений):
   - менеджер загружает файл и вызывает типовое действие;
   - менеджер задаёт вопрос, на который у него нет прав;
   - руководитель спрашивает у бота, что происходит в группе;
   - руководитель исправляет ответ бота → правило попадает в харнес;
   - руководитель добавляет новое типовое действие;
   - добавление нового менеджера и новой группы.
6. **Интеграция с Claude Code + DeepSeek** — как бот вызывает агента (headless-режим / SDK), изоляция рабочего каталога по группе, ограничение инструментов, таймауты, очередь, стоимость, обработка ошибок и fallback.
7. **Механизм самообучения харнеса** — жизненный цикл правила (предложено → черновик → утверждено → устарело), хранение в git, ревью, eval-прогон перед применением, откат.
8. **Безопасность** — хранение токенов и ключей, защита от prompt injection из сообщений и файлов, изоляция данных между группами, аудит-лог, бэкапы.
9. **Развёртывание и эксплуатация** — Docker Compose, CI/CD, мониторинг, логи, алерты, обновление без простоя.
10. **Этапы** — MVP → v1 → v2, для каждого этапа: состав задач, критерии готовности, примерная трудоёмкость, риски.
11. **Открытые вопросы и риски**, которые зависят от ответов на опросник.

## Формат результата

Сохрани в репозиторий:
- `docs/research.md` — результаты исследования со ссылками;
- `docs/questionnaire.md` — опросник для заказчика;
- `docs/plan.md` — план реализации (с диаграммами Mermaid).

Пиши на русском языке, кратко и по делу, технические термины оставляй на английском. Там, где решение зависит от ответа заказчика, явно помечай: «**Зависит от вопроса №N**», и указывай вариант по умолчанию. Не пиши код приложения — только план, структуры, примеры конфигов (YAML) и примеры промптов, где они проясняют замысел.
